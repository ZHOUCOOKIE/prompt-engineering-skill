# Sources

Snapshot date **2026-11-09**, the day Claude Fable 5.2 and Claude Mythos 5.2 shipped. Anthropic's documentation is revised frequently — during the life of this repo one page reversed its recommendation mid-verification, another was withdrawn outright, three model releases moved model pages to new paths and re-opened every model-specific claim, and the Claude Code best practices page was rewritten between two rounds — so where this repo and the live docs disagree, **the live docs are correct**.

What the 2026-11-09 round found is in [The 2026-11-09 re-check](#the-2026-11-09-re-check) below; the 2026-10-23, 2026-09-22, 2026-09-03 and 2026-08-08 rounds are kept after it as history. Those older sections describe the repo as it stood then: several rules and snippets they mention were removed in this round.

**Which sources count.** From this round on the skill takes its rules only from Anthropic's own sites: platform.claude.com/docs, code.claude.com/docs, anthropic.com, the claude.com articles (formerly claude.com/blog), claude.dev/blog (Anthropic's developer blog, which the Claude Code documentation links to), support.claude.com, and the Claude Code changelog. One public employee statement is kept and labeled as such (see Employee talks). Three rules are the repo owner's own and are labeled "User rule, not official guidance" where they appear.

Read-depth legend:

- **Full** — the saved page was read end to end in this round (prose in full; long multi-language code samples skimmed)
- **Targeted** — specific sections were read, or the page was searched for specific terms and the surrounding text read; the rest was not used
- **Linked only** — linked for the reader; nothing was taken from it

## Known conflicts

Where official sources disagree with each other, the resolution used here and why.

### 1. "Best practices for prompt engineering for 2026" (2025-11) vs. the living docs

That post says three things the current documentation contradicts, and a fourth that only looks like a conflict:

| The post says | The living docs say | Resolution |
|---|---|---|
| Prefill the assistant response as an advanced technique | Prefill on the last assistant turn returns 400 from Claude 4.6 onward | **Docs.** Use Structured Outputs or an explicit instruction |
| XML tags are "less necessary with modern models" | Structuring prompts with XML tags is a recommended technique | **Docs** |
| Structured chain of thought in `<thinking>` tags in the reply, and explicit chain-of-thought prompting "even when extended thinking is available" | On Fable 5.2, Opus 5.5 and Sonnet 5.5, a prompt that asks the model to write out its reasoning "might be declined"; rely on thinking instead | **Docs.** See SKILL.md §3.9 |
| "Heavy-handed role prompting is often unnecessary" | Giving Claude a role focuses behavior; even one sentence helps | **Both.** The docs recommend a role and say one sentence makes a difference; the post argues against long personas, not against roles. The skill keeps a short role and cites the post for dropping the persona build-up |

The post also suggests starting with one example and adding more only if the output still falls short, where the best practices page says to include 3–5 examples for best results; the skill follows the page.

### 2. The selection matrix, the selection article and the cost page

The choosing-a-model matrix lists "multistep deep research" among the example uses for Claude Fable 5.2. The cost page measured Fable 5.2 on DeepResearch Bench II at 2.9 times Opus 5.5's cost for a score 1.9 points lower, and 4.7 to 7.0 points below Fable 5.1 at each effort level; its advice beside those figures is "Measure what a more expensive model buys on your own workload." The 2026-11-09 selection article also puts deep research under Fable 5.2. The skill states both and tells the writer to pass both to the user rather than picking one. The matrix and the article's task table also file two kinds of work differently: the matrix puts large-scale refactoring under Opus 5.5 and analysis carried through to a finished document, spreadsheet or deck under Fable 5.2, while the article puts major refactors under Fable 5.2 and everyday documents, slides and spreadsheets under Sonnet 5.5. SKILL.md §2 follows the article's table and notes the difference.

### 3. Default effort for Fable 5.2 differs by surface

Every platform page gives `high` as Fable 5.2's default; the Claude Code model configuration page and the launch announcement give `medium` for Claude Code and the Claude apps. Both are right for their surface, and the skill says which is which. The starting point differs the same way: the selection article's task table starts Fable 5.2 at `medium`, then `high`, while the Fable 5.2 prompting page, the what's-new page, the effort page and the choosing-a-model page say to start at `high`. SKILL.md §2 starts at `medium` for Claude Code and the apps and at `high` for a prompt that runs on the API.

### 4. Verification instructions differ by model

The best practices page recommends a self-check and names Claude Opus 5 as the only exception; the Claude Code documentation says reminders to test or check are usually unnecessary on Fable models; the Sonnet 5.5 and Haiku 5.5 pages each publish a verification paragraph to add at lower effort. These are statements about different models, so SKILL.md §3.4 lists them per model and does not merge them into one rule. Earlier rounds of this repo did merge them, with a reading of its own; that reading was removed in this round.

### 5. When to move from Opus 5.5 to Fable 5.2

Official places put the threshold differently. The selection article (2026-11-09): move up when Opus 5.5 at `high` still falls short, and test Fable 5.2 before raising Opus 5.5 past `high` on a hard task. The choosing-a-model page: when your evals fall short at `xhigh` or `max`. The what's-new page, the models overview and the cost page: when your evals on Opus 5.5 "at higher effort" still fall short. The cost page's "Start here" table, for any model: if you lowered effort, restore it; otherwise try the next tier up at its default effort. SKILL.md §2 follows the article's three steps, because it is the only one of these that puts self-verification first, and `models.md` quotes each of them.

### 6. `xhigh` first in the Claude apps

The support article on app settings says: "For complex coding and agentic tasks on Opus 4.7 or newer, try Extra high (xhigh) first." The Opus 5.5 and Fable 5.2 pages reserve `xhigh` for work where a gain has been measured, and the Sonnet 5.5 and Haiku 5.5 pages use it only where evals show a quality gain. The skill selects by the model pages and tells the writer to pass the support article's sentence to the user as well.

### 7. Which model for everyday coding in Claude Code

On where to start at all, the choosing-a-model page offers two routes: efficiency-first (implement with Haiku 5.5 and upgrade only for specific capability gaps; for prototyping, tight latency, cost-sensitive work and high-volume straightforward tasks) and capability-first (Opus 5.5). The selection article and the selection matrix start most work on Opus 5.5. SKILL.md §2 follows the task table and tells the writer to mention the efficiency-first route when the task is one of those cases.

The selection article and the Claude Code best practices page start everyday engineering on the default, Opus 5.5 ("the default Opus 5.5 handles most coding well and Sonnet costs less on routine work"). The Claude Code costs page says: "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions or multi-step reasoning." SKILL.md §2 follows the article's task table: Sonnet 5.5 for well-scoped coding, Opus 5.5 for other everyday engineering.

### 8. Asking for less thinking in the prompt

The Claude Code model configuration page says you can ask Claude in a prompt or in CLAUDE.md to think more or less often, and the model responds within its effort setting. The Fable 5.2 page says such a line did not stop the model from thinking at `medium` and above, the Haiku 5.5 page says it did not stop that model from thinking, and the Sonnet 5.5 page says it does not reliably reduce thinking. SKILL.md §3.10 follows each model's own page.

### 9. The Opus 5 effort starting point — a documentation change, kept as history

During the first review, two independent passes reported that the Opus 5 recommendation was "start at `high`" while three direct fetches of the page said `xhigh`; a day later the page had changed and the reviewers were right. The lesson generalizes: **a snapshot of fast-moving documentation is wrong by default, not by exception.**
